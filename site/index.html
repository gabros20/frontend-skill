/frontend

Not “just UI.” frontend owns the production client across creative websites, web apps, and dense product UI — plus native iOS and Android. Ask an agent to ship a marketing page or a product surface and you often get a happy-path mock: missing empty/error/loading states, soft a11y, soft Safari video, no CWV budget, no tests. This pack is a faceted router over 27 dense references — load only the job + platform + stack you need, then ship with the full state set and the checks that prove it.

The idea

Not a 30k-token dump of “frontend best practices.” A router for the whole client register — marketing and creative websites as much as dense application UI. Name the engineering job, pick the surface, optionally name the stack — then read only those files completely before writing code. Unrelated craft never enters the context.

Native overrides web. A SwiftUI screen never loads web-platform CSS rules. An uncovered stack (Vue, Svelte, Astro, …) still gets the core job + platform substrate; project conventions win.

1 · Primary job

Exactly one core task: state-and-data, forms, performance, client-security, client-app-wiring, …

2 · Platform

Web by default (web-platform-css + runtime). Or SwiftUI / Compose / Expo RN — mandatory when the target is native. Expo is the default RN path.

3 · Stack overlay

React, Next, Tailwind, shadcn — only when the project actually uses them. Skip for uncovered stacks.

The non-negotiable laws

Universal invariants — they apply even when the owning reference is not open.

  • Project conventions winStack overlays sharpen doctrine; uncovered stacks follow the repo. Never invent a second design system.
  • Ship the full state setInteractive: default / hover / focus-visible / active / disabled / loading. Data: empty / error / success. Happy path alone is incomplete.
  • Reduced motion is a complete alternativeSwap to a legible no-motion state — never freeze mid-transition.
  • Accessibility floors are constraintsContrast, target size, focus, keyboard — cite accessibility.md numbers, don’t redefine them.
  • A green build is not a correct screenServe · screenshot two viewports · reduced motion · interact. State what ran.
  • Never present untested code as verifiedIf tests or screenshots were skipped, say so with evidence.
  • Preserve design intentImplement a handoff faithfully; report conflicts instead of silently overriding brand or architecture constraints.
